# L02d1: QEMU harness, boot and capture

## Terms

- **Harness** — [`evals/e1000/harness/`](../evals/e1000/harness/): a host-side Python driver
  and a guest init script that boot two QEMU guests and run named scenarios against them.
- **DUT** (device under test) — the guest with QEMU's emulated Intel 82540EM, whose driver
  module a scenario loads. **Peer** — the second guest, with a virtio-net card.
- **Reference driver** — Linux v6.12's in-tree `e1000`. The **candidate** (`e1000_l02`, from
  L02e) is not run in this unit.
- **Register trace** — QEMU's log of every guest read and write to the e1000's registers.
- **FAIL / ERROR** — a scenario verdict. FAIL: a guest misbehaved, which a driver can cause
  (exit 1). ERROR: the harness or the host did, for example a guest that never booted
  (exit 2, as for bad arguments).
- **Review swarm** — the `review-swarm` skill: four reviewer agents with narrow mandates, a
  mechanical check that drops any finding it cannot quote from the code, and a referee.
- **Operator** — the coordinating agent session that wrote the harness and this record.

See the [glossary](../../../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md) (O3; the harness
halves of A3, A4, A6), the [plan](../IMPLEMENTATION-PLAN.md) (L02d, L02d1), and the
[lab notebook chapter](../notebook/L02d1.md).

## Design choices

- **Commands on a second serial port.** Each guest runs a shell loop on ttyS1; the kernel
  console stays on ttyS0. Scenario logic runs on the host, so one scenario can drive the DUT,
  the peer and the DUT's QEMU monitor (QMP, for link toggling in L02d2) in turn.
- **No option ROMs.** Both NICs get `romfile=`, so the BIOS never runs iPXE against the e1000
  before Linux: the trace and the device state begin with the driver under test.
- **Addresses** on the test link are 192.0.2.0/24, a documentation range.
- **Trace capture:** `memory_region_ops_read/write` filtered to the e1000's MMIO and I/O
  regions, `pci_cfg_read/write` for its configuration space, and QEMU's `e1000*` model
  events, each line timestamped. The raw trace is kept, gzipped.

compatibility, docs-versus-code) delivered; the mechanical check dropped nothing; the referee
kept 17 of 22 findings after merging 5 into others and lowered 3 from medium to low.
Survivors: 1 medium, 16 low. The user chose to fix all but F14 and F15.

## Open limitations

- The late-connect race F4 fixed was not reproduced live; the fix rests on the guest
  repeating READY until its first command, and on fourteen passing smoke runs across the
  last two fix rounds.
- `--accel tcg` was not run; every run here used KVM.
- Only `smoke` and the two self-tests exist. The design's scenario list, the ITR read-back
  decision, the L02e open-item probes, per-phase trace grouping and the planted defects are
  L02d2's.
- Smoke does not inspect the kernel log: a driver that logs a warning, a call trace or a
  transmit hang but still passes its pings would PASS, and the saved log is taken before
  `rmmod`. Raised by the fix reviewer; assigned to L02d2.
- The EEPROM check shows that the driver used the EEPROM interface, not that the MAC came
  from it. EEPROM access through the I/O-port window would not be counted.
- Scenarios skipped after an ERROR leave no entry in `verdicts.json`.
- The peer uses the same kernel as the DUT; a defect in the kernel's own networking would
  affect both ends alike.
