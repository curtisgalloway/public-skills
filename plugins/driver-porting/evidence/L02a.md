# L02a: pin sources and write the blind requirement list

## Terms

- **Blind requirement list** — critical e1000 requirements (the design asked for about 50;
  the frozen list has 60) written from the Intel manual before any spec exists, used in L02c
  to measure what the spec missed (design D4). It is the lightweight counterpart of the
  ENC28J60 ledger and borrows its
  [row format](../evals/enc28j60/LEDGER-FORMAT.md).
- **Author** and **second reader** — two fresh agent contexts given only the manual and their
  briefs (and, in later rounds, each other's reports). The author wrote the rows; the reader
  checked each against the section it cites.
- **Pin** — an exact identity (edition, commit, hash, package version) recorded so a later
  unit can check it is using the same input.
- **Test host** — the x86-64 machine that will run QEMU in L02d.

See the [glossary](../../../GLOSSARY.md), the [plan](../IMPLEMENTATION-PLAN.md) (L02a), and the
[design](../QEMU-DIFFERENTIAL.md).

## Blind requirement list

**Format.** The ENC28J60 ledger's row schema, trimmed: `id` (`E1000-<FACET>-<NNN>`, never
renumbered), `statement` in the author's words, `class` (`documented-hardware-requirement` or
`inference` with `premises`), `derivation` (manual section and heading, register or table),
`weight` (`critical` or `important`), `in_scope`, `status`, `notes`. Facets: PCI, INIT, EEPROM,
PHY, REG, RX, TX, IRQ, STAT. The ledger's applicability columns are dropped: they track errata
by silicon revision, and the 8254x specification update is not an input to this list.

**Scope.** 82540EM core path with legacy descriptors: PCI configuration and BAR access, reset
and initialization, EEPROM MAC read, PHY access and link, receive and transmit rings, interrupt
cause, mask and throttling, statistics, and teardown. The design's non-goals are excluded.

The list stays in the private run store until L02c. Publishing it here would let the L02b spec
author read the answer key, and recall measured against a list the author had seen would mean
nothing. For the same reason this file gives counts and row IDs only, never what a row says;
the findings' substance is in `READER-REVIEW.md` and `RESOLUTION.md` in the run store. L02c
publishes the list beside the recall result; this hash is what that copy is checked against.

## Process

1. **Author.** A fresh Claude Opus 5.5 subagent received a brief and a directory holding only
   the manual (PDF and text). The brief forbade driver source, QEMU source, the web, and any
   other file. It drafted 93 rows, trimmed them to 58 to fit the brief's 45–60 range, and listed
   the dropped items in its notes.
2. **Second reader.** A second fresh Claude Opus 5.5 subagent, with the same restrictions,
   checked every row against its cited section before it could see the author's notes:
   47 agree, 11 agree-with-fix, 0 disagree, 0 out of scope, and 4 missing critical
   requirements proposed.
3. **Resolution.** The author checked each of the 15 findings against the manual: 13 applied,
   2 applied with modifications, 0 disputed. It split 5 compound rows, withdrew 1 duplicate,
   and added 3 transmit rows and 1 PHY row.
4. **Confirmation.** The second reader checked the two modified resolutions and every new or
   changed row: 21 accepted, 0 objections. It added one locator note on INIT-004, which the
   operator applied before the freeze. That is the only edit made outside the two agents.
5. **Mechanical check.** `check_requirements.py` (in the run store) checks id form and facet,
   per-facet numbering, duplicates, required fields and enums, that every inference has
   premises, and that every cited section number exists as a heading in the manual text.
   It passed on the frozen list. It was first shown to fail on a copy with a bogus section,
   a page-number-only locator, and a duplicate id (six problems reported, exit 1).

### Conflicts inside the manual

The author found five places where two sections of the manual disagree. Four are recorded in
the notes of active rows; the fifth concerns a row dropped in the trim and is recorded only in
`AUTHOR-NOTES.md`. Of the four active rows, two take the register definition's reading, one
pins only the value both sections agree on, and one accepts either reading, which the ledger
format would class `unresolved-conflict`; the trimmed format has no such class, so it is
carried in the row's notes. Which rows these are stays private with the list.

## Isolation audit

Both agents' tool logs were read after each turn, from the harness's session transcripts, and
are retained in the run store under `logs/`. Every file each opened was in its own directory
(the manual, the briefs, the list, and the reports) or in the operator session's scratch
directory (PDF pages rendered to images, edit scripts), now copied to `scratch/`. No tool call
named a driver or QEMU path or a URL, and neither used web search or fetch. The second reader
did not open the author's notes or draft before its round-1 verdicts, as its brief required.
The Linux files were extracted to a separate evaluator-only directory neither agent was given.

The reader's round-2 check preceded the operator's INIT-004 locator addition; the reader
requested that addition but did not see the edited row.

This establishes what the agents read in this run. It cannot exclude what the model learned in
training: the Linux e1000 driver is public and old, and a Claude model has likely seen it. Both
agents cited a manual section for every row and the reader checked each one, so no row rests on
memory alone, but the choice of what to include may still reflect it. The L02b spec author and
L02e implementer are the same model family; recall in L02c should be read with that in mind.

## Review

The unit's review has two parts.

- **The list:** the second reader's two rounds above, retained as `READER-REVIEW.md` and
  `RESOLUTION.md` in the run store.
- **The public changes** (this file and the plan update): a fresh Claude Opus 5.5 reviewer
  subagent before commit, retained as `logs/precommit-reviewer.jsonl`. The plan's method for a
  documentation unit, `consult`, goes through Codex, whose quota is exhausted; the fresh
  reviewer is the fallback. It checked every hash, count, and ID above against the run store
  and found them correct against the run store's records (the QEMU binary hash against the
  recorded pin, not recomputed on the test host), and returned 2 blocking and 6 should-fix
  findings. Blocking: an
  unfilled review line, and the draft of this file publishing the substance of about a dozen
  rows while the plan told the L02b author to carry the manual's conflicts into the spec, which
  would inflate the recall L02c measures. Should-fix: tool logs claimed retained but not in the
  store; the conflict summary overstated; the limits section wrong on the row count and on
  dropped rows; the checker's totals include the withdrawn row; the QEMU pin had no fetch
  source; and plan gaps (L02a's acceptance line removed, the no-read rule missing from L02b,
  the manual copy to use, the track count). All were fixed as described in this file and the
  plan. A second round by the same reviewer found no blocking issue and one should-fix (a
  locator title and a phrase that together hinted at one row's topic), fixed before commit,
  plus three wording nits, also fixed.

## Limits

- The list is written from one edition of one manual. The 8254x specification update (errata)
  was not an input, so no row reflects an erratum.
- 66 rows is a sample, not the full requirement set. The author's draft had 93; some items it
  dropped in the trim came back through the reader's missing list, and the rest are listed in
  its notes and are not in the recall denominator.
- Weight is a judgment made before any driver exists.
- The QEMU package version is recorded; the source of that build was not read and is not a
  spec input, by design.
