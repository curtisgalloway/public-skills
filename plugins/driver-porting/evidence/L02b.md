# L02b: author the 82540EM core-path spec

## Terms

- **Spec** — the clean-room implementation spec for the Intel 82540EM (e1000) core network path.
- **Clean-room reader** — an agent allowed to read the encumbered (GPL) Linux driver; it passes
  on hardware facts in its own words, never code.
- **Transfer review** — the `cleanroom-spec` gate: a fresh verifier runs the leak scanner and
  checks leaks, structure, attractants, and the usage notice. It does not judge accuracy.
- **Provenance tag** — the label on every fact: `[databook]` (Intel manual), `[standard]` (PCI,
  IEEE 802.3), `[source-observed]` (seen only in the driver), `[inference]`, `[kernel]` (Linux
  `include/` or `Documentation/`).
- **Ledger** — the run's provenance ledger: one line per spec revision, verdict, and transcript.

See the [glossary](../../../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md), the
[plan](../IMPLEMENTATION-PLAN.md) (L02b), and the [L02a evidence](L02a.md).

## Isolation

The plan requires that the spec author never read the L02a blind requirement list, so that
L02c's recall stays a measurement.

- Every agent was given only the new run's paths. None was given the L02a run path, and each
  was told not to open other run directories, this repository's `evidence/`, QEMU source, or
  the web.
- The operator context read neither the blind list nor any draft before it passed transfer
  review.
- A mechanical audit of the author's transcript and of both nested readers' transcripts found
  no tool call that touched the L02a run, the blind list, `evidence/`, or QEMU. Every match
  was a prohibition being passed down to a subagent.
- The author made no web fetches. It cites the PCI and IEEE 802.3 references at clause level,
  without fetching them.
- One weakness: a nested clean-room reader wrote its facts report into the operator session's
  scratch directory, not the run store. The operator listed the filename and moved the file
  into the run store without opening it.

| Criterion (plan) | Evidence |
| --- | --- |
| Transfer review PASS | Transfer review 3 PASS on SHA-256 `b93d7ef0…d11f`. The landed file's hash matches the ledger line. |
| Every fact tagged | Acceptance review 1 criterion B, and transfer review 3's check of every ordered sequence. Revision 3 carries 243 `[databook]`, 23 `[standard]`, 53 `[source-observed]`, 45 `[inference]` and 46 `[kernel]` tags. |
| Scope and non-goals match the design | Acceptance review 1 criterion C: core path, non-goals and frame sizes match; scope unchanged in revisions 2 and 3. |

The spec covers:

- PCI discovery and BAR mapping
- reset
- EEPROM MAC read with checksum
- PHY and link over MDIC
- legacy receive and transmit rings
- receive filtering
- interrupt cause and mask, throttling and delay timers
- statistics
- flow control as far as initialization requires
- teardown
- the Linux v6.12 integration, citing `include/` and `Documentation/` only, with no in-tree
  driver

Accuracy was sampled, not verified. Acceptance review 1 checked 13 `[databook]` facts against
the manual, and all 13 matched; timing values were checked on the rendered PDF pages. Reviews
2 and 3 checked every changed fact against the manual.

## Review method

The plan's documentation review (`consult` with the other coding agent) was unavailable
because the Codex quota was exhausted. The fallback was a fresh reviewer subagent at each
round; all reviewers and verifiers were Claude Opus 5.5, the same model family as the author.
Their reports are retained in the run store's `review/` directory.

## Open findings carried to L02c

None of these blocks L02b. L02c produces a spec revision anyway.

- **NB-1.** §5.1 cites a `[kernel]` source for an ordering note inside the hardware half. That
  breaks the spec's own tag rule, which allows `[kernel]` in the hardware half only in §8.
- **NB-2.** §5.2 R7 (CTRL.RST reloads the EEPROM) is `[inference]`, but the manual's EEPROM
  reload list does not include CTRL.RST. Its confidence is overstated, and its check would
  pass either way; the default action (a 5 ms wait) is safe.
- **NB-3.** §5.1 P1 cross-reference: it says "§5.2 R4" where it should say "R5".
- **C-2.** The spec does not define how the ITR value is read back. This is a harness decision
  for L02d, for example taking it from the register trace.
- **Transfer review 3 advisories.** One `[source-observed]` placement relies on the blanket
  caveat. The probe order in §10 differs from the section order in §5.

## Limits

- Transfer review is a leak-and-structure gate, not an accuracy check. The first transfer
  review passed a structural defect that the second caught, so one verifier reading is not
  enough; L02c's two readings are the accuracy gate.
- Author, editors and reviewers share a model family, and that model may have seen the Linux
  e1000 driver in training.
- The APFS extraction of `include/` may have merged case-colliding paths. This affects reading
  only; no build ran in this unit.
- Transcripts from the first six agents were copied into the run store. From 2026-09-23 on,
  transcripts are recorded by path in the ledger instead. Those paths are temporary files that
  are not retained.
