# L02e: implement, build, and review the candidate

## Terms

- **Candidate** — `e1000_l02`, the new Linux driver for the Intel 82540EM written in this
  unit from the clean-room spec. The in-tree Linux `e1000` driver is the **reference**.
- **Implementer** — the fresh agent that wrote the candidate. It was given the spec, the Intel
  manual, and Linux `include/` and `Documentation/`, and forbidden any Ethernet driver source.
- **Spec gap** — a question the spec could not answer, filed by the implementer in the run's
  spec-gap log. A **spec error** is a place where the spec was wrong.
- **Repair round** — one bounded fix pass on findings the user selects, followed by a review
  of the diff.
- **Review swarm** — the `review-swarm` skill: four reviewer agents with narrow mandates
  (security, correctness, compatibility, docs-versus-code), a mechanical check that drops any
  finding it cannot quote from the code, and a referee.
- **W=1** — the Linux build's extra-warnings level.
- **Operator** — the coordinating agent session that prepared inputs, briefed and launched
  the other agents, and wrote this record. It wrote no driver code.
- **Blind list** — the 66 active requirements written from the Intel manual in L02a before
  any spec existed ([`requirements.yaml`](../evals/e1000/requirements.yaml)).

See the [glossary](../../../GLOSSARY.md), the [design](../QEMU-DIFFERENTIAL.md) (O2, A2), the
[plan](../IMPLEMENTATION-PLAN.md) (L02e), and the [lab notebook chapter](../notebook/L02e.md).

## Status

**Complete, 2026-09-24.**

The candidate builds against the pinned Linux v6.12 x86-64 tree with zero warnings at the
default level and at W=1. Three independent reviews found no critical defect; the
requirements review found all 60 critical rows of the blind list implemented. One repair
round fixed seven of eight selected findings, and the eighth was declined correctly. Nothing
has loaded or run the driver: behavior is L02f's job.

Private run ID: `e1000-l02e-20260924-01`. The candidate, its notes, the build logs, every
review report, the repair file, and the ledger stay in the run store. The candidate is licensed
GPL-2.0-only, the brief's choice (a module using the kernel's GPL-only interfaces needs a
GPL-compatible license), and is not published in this repository.

## Build environment

On the test host (x86-64, Ubuntu 26.04.1), the verified v6.12 archive (`8787cc90…0caa`) was
extracted to ext4 and matched the upstream tree `ac4266cc…` in full (86,618 files and 62
symlinks) before any build. Configuration: `x86_64_defconfig` with `CONFIG_E1000=m`.

The host's only compiler, GCC 15, cannot build v6.12: ACPI header strings trip
`-Werror=unterminated-string-initialization`. The user chose installing `gcc-14` (14.3.0); the
kernel then built with exit 0, zero warnings, `kernel.release` 6.12.0, and the reference
module, `bzImage`, and `Module.symvers` present. The toolchain had not been pinned in L02a.

The implementer built only through a wrapper that copies its directory to the host and runs
an external-module build (`M=`) against that tree, so it needed no shell on the host. A trivial
module built cleanly through the wrapper before the implementer started.

## Isolation

Isolation was by instruction and checked afterward; nothing enforced it (see
[PROCESS-NOTES.md](../PROCESS-NOTES.md) on why no hook was installed).

- **Inputs placed in the run:** the spec, the manual, kernel `include/` and `Documentation/`,
  the brief, the build wrapper, the run's README and ledger, and the implementer's own
  directory. By the operator's account, operator files naming forbidden paths (the review
  briefs and the audit policy) were moved out of the run while the implementer worked; file
  times cannot show this.
- **The implementer's own log:** its `CONSULTED.md` lists only files inside the run and the
  `cleanroom-implementer` skill file.
- **Transcript audit.** The user ran `cleanroom-implementer`'s `session_audit.py` on the
  implementer's transcript: one file, holding both turns, since the repair resumed the same
  agent. Its policy blocked part of the brief's forbidden list: the Linux e1000 file names,
  `drivers/net`, the other runs, the blind list, `evidence/`, QEMU, the test host, and URLs; it
  did not block the rest of the source tree or other Intel drivers by name. **The auditor's
  verdict was `FINDINGS - contaminated session(s)`**, and its prescribed response was to
  discard the candidate and regenerate. The path check found no hits; the 8 findings (5
  license markers, 3 code-shaped results) came from the marker checks.
- **Triage.** At the user's direction a fresh subagent traced each finding to the tool call
  that produced it, reporting targets only. Six came from the implementer reading or editing
  its own driver (two with build-wrapper output), one from the allowed kernel headers, and one
  from the brief, which instructed GPL headers. A scan of every readable tool call found no
  forbidden target. One record was too large for the file-read tool: the Write that created
  the driver file, which sends text out rather than bringing it in, and which the auditor's
  path check covered. On that triage, a judgment rather than the tool's verdict, the user and
  operator kept the candidate and record the findings as explained false positives.
- **The operator:** read the implementer's final reports, its spec-gap entries, and the review
  reports; it did not read the Linux driver, and it ran the leak scanner on the candidate
  without reading the source it compares against.

## Review of the public changes

The plan's documentation method, `consult` with Codex, was started and canceled: the user
reported the Codex quota exhausted for a day. The fallback was a fresh Claude Opus 5.5
reviewer with the same brief (report retained in the run store). It recomputed the hashes
and line counts, recounted the leak-scan identifiers and every review's totals, checked the
build logs and the PR state, and searched the changed files for private names and addresses
(none found).

It returned 1 blocking finding (an unfilled placeholder in this section), 9 should-fix, and 9
nits. Should-fix: a truncated hash in the plan; stale branch and PR state (PR #82 merged
during the unit); a stale notebook header and index; the omitted failed first build; a count
of spec departures; the audit claim, which did not state the tool's FINDINGS verdict or that
its policy covered only part of the forbidden list; a misattributed notebook thread; a process
log entry timestamped when written, not when it happened; and missing terms. Nits included the
unproven first-pass W=1 build, the license sentence, and the unstated next-step decision. All
were applied; corrections to notebook and process-log entries were appended, not edited in.
It could not verify the effort table, the triage, or the operator's account of which files
were in the run, which rest on the ledger and the operator.
