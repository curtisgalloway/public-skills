# L01 first unit: implement, build and independently review the Linux driver

## Terms

- **Candidate** — the new ENC28J60 driver written from the spec in this run.
- **Reference driver** — the upstream Linux v6.12 `enc28j60` driver, used as evidence, not truth.
- **Spec gap** — a question the spec could not answer, filed by the implementer.
- **Repair round** — one bounded fix pass after independent review; the agreed cap is two.
- **Arm** — one `review-swarm` reviewer with a single mandate.

See the [glossary](../../../GLOSSARY.md), the [plan](../IMPLEMENTATION-PLAN.md) (L01), and the
[Linux-priority decision](LINUX-PRIORITY.md).

## Independent reviews

All reviewers were fresh Claude Opus 5.5 subagents, none of which wrote code. Reports are in the
run store.

| Review | Method | Result |
| --- | --- | --- |
| A: candidate vs reference driver | `reference-driver-review`, data sheet as tie-breaker; `anchor_check` 0 errors (207 anchors), `inventory_check` 232 of 232 reference register names mentioned | 26 findings: 2 `[bug]` (impl-error), 2 `[suspect]` (spec-gap), 8 `[ref-issue]`, 14 `[benign]` |
| B: answer-key table | every active critical and important row outside ELEC (124), without reading the reference driver | critical 64/64 implemented; important 54 implemented, 1 partial, 5 out of scope; 0 missing, 0 contradicting |
| C: `review-swarm` | four arms, mechanical quote check, referee | all four arms delivered; 7 verified, referee kept 5 (all low) and dropped 2 as documented intent |
| Repair review | fresh reviewer, diff `59a8156..15dea2c` | all 7 repair items fixed correctly; 5 new low findings; no regression above low |

**The operator checked the reviewers.** Three answer-key verdicts (RX-031, TX-010, PHY-012) were
confirmed against the code. Reviewer A's high finding F-01 rested on the belief that the v6.12
SPI core sets `SPI_CS_HIGH` for GPIO chip selects; the pinned `drivers/spi/spi.c` sets it only
from the `spi-cs-high` property or ACPI, so the finding was repaired but its severity for the
Raspberry Pi is low, not high. F-02 (optional `spi-max-frequency` rejected) was confirmed against
the binding and the SPI core's default in `spi_setup()`.

Reviewer B's one partial row, IRQ-018, is an `observed-software-behavior` row describing the
reference handler's loop structure. The candidate's single pass plus a 100 ms poll is a valid
alternative (reviewer A: B-12, benign); it was not treated as a defect.

Reviewer A also recorded eight defects or weaknesses in the **reference** driver that the
candidate avoids, the most significant being that the reference widens ETXND to the end of
memory before a late-collision retransmit (R-01). These are evidence that "match the reference"
would be the wrong acceptance rule for the second unit.

the implementer caught both spec defects. The practice run's recorded contradiction at RX-031
(receive-pointer initialization) is the same §8.3 defect, now reproduced by an implementer.

## Limits

- No hardware result: no probe, link, or traffic has been observed.
- Every reviewer was a Claude model; the implementer was not. A later Opus 5.5 implementer turn
  would share the reviewers' model family.
- Reviewer A read the reference driver; reviewer B did not. The operator read the reference
  review and the SPI core, and is therefore on the evaluator side for this run.
- This is not a spec-only experiment: the implementer had general Linux knowledge, and access
  control was by instruction and audit. It cannot be relabeled as a frozen trial arm.
