# L02d1 — QEMU harness, first half: boot and capture

Goal: one command on the test host boots a guest with the reference `e1000` and a virtio-net
peer on a point-to-point link, runs a smoke scenario, and stores the register trace, packet
captures, consoles, verdicts and identities per run ([plan](../IMPLEMENTATION-PLAN.md), L02d).
Verdict record: [evidence/L02d1.md](../evidence/L02d1.md).
Terms: the DUT (device under test) is the guest driving the emulated e1000; the peer is the
second guest; the operator is the coordinating agent session. See the
[glossary](../../../GLOSSARY.md).

## 2026-09-24T16:17-07:00 — opening
Starting revision: `a1a37be` (merge of PR #88) on new branch `driver-porting/l02d` in its own
worktree; no pre-existing changes. Private run `e1000-l02d-20260924-01`. The plan's L02d split
point is taken: this unit is boot-and-capture; scenarios and mutations are L02d2.
Reuse: the test host's L02e kernel build (v6.12, `x86_64_defconfig`, `CONFIG_E1000=m`, gcc-14)
already has virtio-net, devtmpfs, initrd and packet sockets built in, so no rebuild. Its
`bzImage` and `e1000.ko` hashes are recorded in the run ledger; QEMU's binary hash matches the
L02a pin. Approach: a stdlib-only Python host driver that runs both guests as command servers
over a second serial port, so scenario logic lives on the host and can toggle the link through
QMP between guest steps.

## 2026-09-24T16:23-07:00 — decision: option ROMs off, TEST-NET addresses, second serial port
Both NICs get `romfile=` so SeaBIOS never runs iPXE against the e1000 before Linux: the
trace and the device state then start with the driver under test. The link uses
192.0.2.0/24 (documentation range). Commands travel on ttyS1 so kernel messages on the
console cannot interleave with command output.

## 2026-09-24T16:23-07:00 — surprise: `-msg timestamp=on` prefixes an ISO time
The trace filter expected the `pid@sec.usec:` prefix; this QEMU writes
`2026-09-24T23:20:21.496397Z <event> ...`. The raw trace held 14,210 `e1000-mmio` accesses.
Fixed the pattern (unit test covers both forms) and added `pci_cfg_read/write` for the
e1000's configuration-space accesses.

## 2026-09-24T16:51-07:00 — dead end: `read -t` in the guest's command loop
busybox `read -t` throws away a partly read line when its timeout fires, and the host's
1 s carrier poll lines up with the 1 s timeout, so commands were lost. Do not use a read
timeout on the command channel. Replaced by a blocking read, with READY repeated by a
background loop that is killed when the first command arrives.
